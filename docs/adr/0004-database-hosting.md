# ADR-0004. Выбор хостинга для базы данных
- Статус: принято
- Дата: 2026-11-11

## Контекст
База данных приложения TimeCapsule ранее работала на отдельном виртуальном сервере (EC2), что требовало ручного администрирования, настройки резервного копирования и установки патчей безопасности. Для повышения надежности, автоматизации рутины и снижения затрат на обслуживание необходимо выбрать управляемое облачное решение для СУБД PostgreSQL.

## Решение
Используем сервис Amazon RDS for PostgreSQL в конфигурации Single-AZ (в одной зоне доступности) на инстансе класса `db.t4g.micro`.

## Рассмотренные альтернативы
- **PostgreSQL на EC2 (предыдущий вариант)**.  
  Плюсы: полный контроль над сервером и настройками ОС, минимальная стоимость вычислительных ресурсов.  
  Минусы: высокие трудозатраты на администрирование, самостоятельная настройка бэкапов и обновлений операционной системы и движка БД.
- **RDS в одной зоне (Single-AZ)**. *(Выбранный вариант)*  
  Плюсы: автоматические резервные копии, установка патчей СУБД в окно обслуживания, управляемый сервис, низкая стоимость (подходит для Free Tier / Dev-среды).  
  Минусы: инстанс находится в одном датацентре; при его отказе база становится недоступной до ручного восстановления.
- **RDS Multi-AZ**.  
  Плюсы: высокая доступность, автоматическое переключение (failover) на синхронную резервную копию в другой зоне без потери данных при аварии.  
  Минусы: стоит в два раза дороже Single-AZ, что избыточно для текущей учебной среды и бесплатного тарифа.
- **Amazon Aurora**.  
  Плюсы: высочайшая производительность, хранилище автоматически реплицируется в 3 зоны доступности, мгновенное восстановление после сбоев.  
  Минусы: высокая стоимость, не подходит для небольших проектов с жестко ограниченным бюджетом.

## Последствия
- **Резервные копии и потеря данных**: RDS делает полные снимки базы раз в сутки (в нашем случае срок хранения установлен на 1 день из-за лимитов Free Tier[cite: 3]), а журналы транзакций (WAL) сохраняются примерно каждые 5 минут. Благодаря механизму Point-in-Time Recovery (PITR), максимальная потеря данных при аварии составит не более 5 минут.
- **Стоимость и ограничения**: База расходует средства за каждый час работы инстанса. Чтобы ограничить расходы, настроено расписание EventBridge Scheduler, которое автоматически останавливает базу на ночь. Однако, по правилам AWS, остановленная база принудительно запустится через 7 дней для применения обязательных обновлений. Если забыть про неё, через неделю она снова начнет потреблять бюджет.
- **Обнаружение базы и отказ зоны**: Приложение находит базу через DNS-запись типа `CNAME` (`db.timecapsule.internal`), которая указывает на Endpoint, выданный AWS. Если зона доступности `eu-central-1a` выйдет из строя, наша база Single-AZ упадет, и приложение перестанет работать. Чтобы всё починить, потребуется вручную восстановить базу из бэкапа в работающую зону (например, `eu-central-1b`) и обновить `CNAME`-запись в Route 53 на новый Endpoint.
